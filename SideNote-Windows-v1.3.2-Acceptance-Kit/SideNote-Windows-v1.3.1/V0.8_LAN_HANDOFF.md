# SideNote Windows v0.8 — experimental encrypted LAN exchange

## Included
- TCP private-LAN encrypted request-response bundle exchange, XChaCha20-Poly1305 AEAD with random 24-byte nonce per packet.
- Random 256-bit pairing key manually shared by user. Listen on port 43861 and connect by other PC IP.
- Uses existing SQLite import/export, duplicate detection and conflict review, preserving offline standalone use.
- Packet cap ~5.5 MB, socket timeouts, private-IP restriction.
- Rust unit tests in `lan_sync.rs` for key, address and encrypted packet serialization.

## Not complete / security caveats
- NO proof of real working connection yet: no cargo toolchain in authoring environment.
- Manual out-of-band shared key, NO QR, SAS device identity confirmation, peer revocation, automatic discovery/reconnect or Android.
- Key is held only in UI memory for session; server remains listening until app exits; restarting requires re-entering it. Treat key as highly confidential.
- No TLS certificate identity; possession of secret is the sole peer authenticator. A key leaked to a LAN peer grants access to notes. Do not expose port to internet.
- Imported conflicts deliberately require manual resolution. Existing revision model needs refinement for robust long-term multi-hop sync; v0.8 is an experimental two-PC test step, NOT release-ready automatic syncing.
- Firewall may block inbound connections. The sync key and network addresses are not sent to any cloud service by this code.

## Acceptance
1. Compile `cargo test` and `npm run tauri build` on Windows, fixing errors.
2. Run Windows A and B on the same LAN; A generates key and starts server, B enters same key and A's private IPv4, presses Sync.
3. Verify A→B and B→A notes after sequential transfers.
4. Verify wrong key is rejected, public destination IP is rejected, oversized packets rejected.
5. Sync twice with no duplicates; divergent edits show in conflict review; deletions propagate with tombstones.
6. Restart each app, test offline note creation then reconnect, and ensure no data loss.
7. Do not claim mobile sync support or production security review until separately implemented.
